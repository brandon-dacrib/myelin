# 08. End-to-end encryption support

Wave 2, code starts week 8; the data model and the concurrency design start day one.

**Expert profile.** Server-side E2EE semantics (device keys, one-time and fallback keys, cross-signing, key backups, device-list tracking), familiarity with `matrix-rust-sdk` and vodozemac from the client side.

**Mission.** Every server-side primitive encryption clients and encrypted bridges rely on, with the two failures users actually see (double-claimed one-time keys, stale device lists) made impossible by construction. See `PLAN.md` section 5.5.

**Owns.** `hs-e2e`: device key upload and query (local and remote, cached, with `msc4263` limits), atomic one-time-key and fallback-key claims, `/keys/changes`, cross-signing upload and signature upload including the admin replacement path, key backups with versions and `etag` and `count` semantics, device-list tracking for remote users (resync, cache) and outbound device-list pokes to federation and appservices, to-device messaging (local, federation, appservice MSC4203), dehydrated devices (MSC3814), rendezvous endpoints (MSC4108, MSC4388) with 07, appservice key proxies (MSC3983, MSC3984) with 11, the `/user/keys/*` and `/user/devices` federation endpoints with 06, `m.key_backup` account data hooks.

**Provides.** Week 8 onward: cursors for 05 (device-list changes, one-time-key counts, to-device); device-list EDUs for 06; MSC3202 transaction fields for 11.

**Consumes.** 07 (devices), 06 (client), 05 (session protocol), 11 (registry), 01.

**Day-one work.** Data model; the atomic claim design as a transactional operation that holds on every backend from 01; the device-list change stream and remote cache design; the to-device queue design; the test plan with `matrix-rust-sdk` (two clients establish sessions, verify, back up and recover on a new device; a bridge bot with MSC4190 encrypts and decrypts).

**Phase 0 deliverables.** Model and tables; property tests proving no double claim under concurrency on in-memory, Fjall and PostgreSQL; to-device queue prototype.

**Phase 1 and 2 deliverables.** Everything in "owns"; federation integration; appservice integration; dehydrated devices; QR login; batching for `/keys/query` performance.

**Definition of done.** `matrix-rust-sdk` E2EE suite green; Complement keys tests green; concurrency property tests green on all backends; differential tests against Synapse for `/keys/query` and `/keys/claim` response shapes.

**References.** Spec E2EE sections; `refs/synapse/synapse/handlers/e2e_keys.py`, `device.py`, `devicemessage.py`, `e2e_room_keys.py` (behavior, AGPL, read only); `refs/ruma/crates/ruma-client-api/src/keys`; the `matrix-sdk-crypto` crate for client expectations; MSC3202, MSC4203, MSC3983, MSC3984, MSC3814, MSC4108.

**Open questions to settle first.** Remote device-list resync policy; to-device retention; whether large key backups belong in the object store.

**Risks.** Any regression here surfaces as undecryptable messages, which users blame on the server; the property tests and the SDK suite are the guard.
