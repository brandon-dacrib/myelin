## Findings (by severity)

1. **Bulk media operations answered with a `Location` that 404'd.**
   `crates/hs-admin/src/media.rs` `PurgeRun::run` built a `Task`, answered `202` with
   `Location: /api/v1/tasks/{id}`, and never stored the task, so `tasks.get` could not find it.
   Fixed (commit "A bulk media deletion's Location header names a task the Tasks API can find"):
   when `state.tasks` is wired, the finished task is recorded with
   `TaskRegistry::record_finished`, and `bulk_delete_takes_local_media_unused_since_the_date_and_spares_the_protected`
   now follows the Location. Still open (queue 2g): run the purge on `state.tasks.spawn` so
   that it can be cancelled and reports progress. That changes the answer from a finished task
   to a running one, and `web/src/pages/media/BulkMediaDialogs.tsx` (`purgeResult(task)`)
   would have to poll `tasks.get`. That is too large to do inside a merge.
2. **`media.scanning.icap.preview` has no control in the Configuration page (decision 0010).**
   `web/src/test/fixtures/hs-config-schema.json` predates `bootstrap-only-config`'s
   `crates/hs-config/src/scanning.rs`. Regenerated from `schema_for!(Config)`, it makes
   `web/src/lib/config-model.real-schema.test.ts` fail with
   `["media.scanning.icap.preview"]` as unsupported. `PreviewMode` is externally tagged
   (`"negotiate" | "off" | {bytes: N}`), and `variantInfo` in `web/src/lib/config-model.ts`
   only knows internally tagged object variants. Fix (queue 2b), either: (a) track 16 teaches
   `config-model.ts` a unit-or-newtype variant kind (a select, plus a number input for
   `bytes`), or (b) track 13 reshapes `PreviewMode` as `{mode: negotiate|off|bytes, bytes?: N}`.
   Then commit the regenerated fixture, and add a Rust test in `hs-config` that compares the
   fixture to `schema_for!(Config)`, so this drift fails CI. The fixture stays stale for now,
   so that `npm run check` stays green.
3. **Merge fallout, fixed.** (a) `crates/hs-admin/src/router.rs`
   `authorized_request_to_undeclared_handler_is_501` asked `/api/v1/reports` (tokens branch)
   or registration tokens (reports branch). Both are real now, so it asks `/api/v1/migration`.
   (b) `web/src/mocks/handlers.ts` lost an `import {` in my union of the media merge,
   restored. (c) `MediaRecord` gained `last_accessed_ms` in `media-admin`, and the
   `reports-tasks-stats` initializers in `crates/hs-media/src/usage.rs` and
   `crates/hs-cli/src/statistics.rs` lacked it. Fixed in the media merge commit. (d)
   `FederationState` initializers in `transport/membership.rs` (added by membership) and
   `transport/keys.rs` (added by EDUs) each lacked the other branch's field. Fixed in the EDU
   merge commit.
4. **`web/src/api/schema.d.ts` was stale on two branches.** `bootstrap-only-config` and
   `reports-tasks-stats` edited `openapi.yaml` without running `npm run generate:client`.
   Regenerated after the merges (commit f2cfa87). Fix going forward: a CI step that runs
   `generate:client` and fails on a diff.

## Seam issues

- `AdminState` has grown to one `Option<Arc<dyn …>>` per area plus a `with_*` builder, and
  every admin branch conflicts on the same three places in `router.rs`. Not a bug; the cost of
  parallel admin work is one union per branch. If more areas land in parallel, consider giving
  each area its own `register(builder)` function the way `hs-federation`'s transport modules do.
- `hs-federation`'s `FederationState` is built by hand in twelve places, so every new field
  touches all of them, and branches built in parallel each miss the other's field. A
  `FederationState::for_tests()` (or a builder with defaults) would remove the class of
  conflict. Owner: track 06.
- Ownership: `federation-membership` edited `hs-room`, `hs-user` and `hs-cli`;
  `registration-tokens-server-notices` edited `hs-auth` and `hs-room`; each says so in its
  status file (06, 15). This is accepted as cross-cutting work that was recorded.
- No AGPL text found. A grep of the merged diff for Synapse module paths and copyright holders
  finds only a reference to Synapse's `app_service_config_files` key in a migration note.
- Decisions recorded: 0010 (`docs/decisions/0010-administered-through-the-api-and-interface-only.md`),

### Findings

1. **Two `formatBytes` functions in `web/src/lib/format.ts`.** `media-admin` added a decimal
   one (`2.4 MB`, number only) and `admin-web-pages` a binary one (`38.0 GiB`, `—` for a missing
   size). The merge left both definitions and conflicting tests. The binary one is kept, in the
   merge commit, because it is the superset of the two signatures and Statistics shows GiB-scale
   totals. Follow-up commit: the Media page states sizes in MiB, and
   `web/src/pages/media/BulkMediaDialogs.tsx` takes its size floor in MiB (×1024², was
   ×1,000,000), so the number typed matches the number shown.
2. **The mock's bulk media deletions answered a Location its task store did not have.**
   `purgeMedia` in `web/src/mocks/handlers.ts` answered `202` with `/api/v1/tasks/{id}`, and
   `web/src/mocks/data/tasks.ts` never saw that task. The real server has recorded it since
   df9616e. Fixed with `recordFinishedTask`, and `MediaPage.test.tsx` checks that the task is
   listed. The audit log already links `task` targets to `/tasks/$taskId`
   (`web/src/lib/audit.ts`), so a `media.delete_bulk` entry now leads to a real page in both
   modes.
3. **Nothing broke in the federation merge.** No textual conflicts. `FederationState` is
   unchanged, every `edu_sink`/`invites` initializer from the first round still compiles, and
   all callers of the new `make_join`/`make_membership`/`send_join`/`send_membership` signatures
   build.
