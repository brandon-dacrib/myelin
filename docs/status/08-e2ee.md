# 08. End-to-end encryption support: status

Track brief: `docs/workstreams/08-e2ee.md`. Owner crate: `hs-e2e`. This session's assignment also
covers `crates/hs-loadgen`'s encrypted scenario (`crates/hs-loadgen/src/scenario_encrypted.rs`).

Last updated: 2026-09-19 (session: real encrypting-client scenario against `hs serve`, run to
completion; this is also the first session to write this file -- `crates/hs-e2e` already existed,
fully built, from earlier work that never left a status file behind. This file therefore covers

## This session's task

Prove the server-side E2EE surface (`/keys/upload`, `/keys/query`, `/keys/claim`,
`/keys/device_signing/upload`, `/sendToDevice`, `/room_keys`, device-list tracking) actually works
against a real encrypting `matrix-sdk` client, not just this workspace's own test helpers, which
necessarily speak the server's own dialect (the same exercise track 05 ran, unencrypted, earlier
this session, which found two real bugs in `hs-room`). Fix what breaks in `hs-e2e`; report what
can't be fixed here.

**Result: every `hs-e2e` route worked correctly on the first run against a real encrypting
client. No bug was found or needed fixing in `hs-e2e` itself this session.** The scenario did
surface a real, concrete failure -- but it is entirely in `hs-user`'s `GET /sync`, which has never
wired in the E2EE cursors `hs-e2e` already provides. See "Bugs found in other tracks" and
`docs/rfcs/0013-e2ee-sync-extensions.md`.

## Done

- **`crates/hs-loadgen/src/scenario_encrypted.rs`** (new, alongside track 05's existing
  `scenario.rs`, which is untouched): two real `matrix-sdk` 0.19 clients built with
  `e2e-encryption` enabled, against a real, separately spawned `hs serve` subprocess (same harness
  as `crate::scenario`). In order:
  1. Register two encrypting clients; a baseline `/sync` for each (this is what actually triggers
     `matrix-sdk`'s automatic `/keys/upload` of a real device identity and a real batch of
     one-time keys -- nothing in this scenario constructs a key by hand).
  2. Confirm bob's one-time keys actually landed, by re-POSTing `/keys/upload` with an empty body
     (this route's own contract: always returns current `one_time_key_counts`) and checking it's
     non-zero.
  3. `/keys/query` shape check, both directions: not just 200 OK, but the exact `device_keys`
     shape a real client parses (`algorithms`, `device_id`, `keys`, `signatures`, `user_id`,
     with both a `curve25519:` and an `ed25519:` entry under `keys`).
  4. Create a room, invite, join (mirrors `crate::scenario`), then turn on encryption
     (`m.room.encryption`, sent directly rather than through `Room::enable_encryption`'s internal
     sync-wait loop, and picked up by an explicit `sync_once` on both sides).
  5. Bootstrap cross-signing for alice (`Client::encryption().bootstrap_cross_signing(None)`,
     `POST /keys/device_signing/upload` -- no UIA needed, matching this route's documented gap).
     Shape-checks bob's `/keys/query` for alice: `master_keys`/`self_signing_keys` present and
     correctly shaped, `user_signing_keys` correctly *absent* (that field is only ever returned to
     the user it belongs to -- verified as a real privacy check, not just a shape check).
  6. Device-list-change check: does bob (who shares a room with alice) see alice's cross-signing
     upload in his next `/sync`'s `device_lists.changed`? Checked directly against the raw wire
     response (`matrix_sdk::sync::SyncResponse` does not expose `device_lists` to callers at all).
  7. The real round trip: alice sends an encrypted message. `Room::send` transparently claims one
     of bob's real one-time keys (`POST /keys/claim`), establishes an Olm session, shares the
     Megolm room key over `PUT /sendToDevice`, then sends `m.room.encrypted` -- reaching a real
     event id here already proves both calls worked (a failure at either step would have made
     `room.send()` itself return an error). Bob then syncs and the scenario checks whether he
     *decrypted* the message -- the assertion that matters, not any individual HTTP status.
  8. Atomic one-time-key claim under real concurrency: `alice_otk_count + 3` concurrent,
     unsynchronized `/keys/claim` HTTP calls (real OS connections, not an in-process race) for the
     same `(user, device, algorithm)`, run against alice's key pool (deliberately not bob's, which
     step 7 partially consumed) once the real flow above no longer needs it. Asserts no one-time
     key is ever handed to two callers, and exactly as many calls succeed as there were keys.
  - Steps 6 and 7's decrypt check both hit the same known gap (see below) and are **soft-failed**
    with a `KNOWN BUG` log line naming the exact route/field and root cause, per this crate's own
    convention (`crate::scenario`'s existing display-name gap) -- not deleted, not hard-failed.
  - Everything else is a hard assertion; the test overall passes
    (`cargo test -p hs-loadgen --test real_client_encrypted` is green).
  - `cargo fmt -p hs-loadgen` clean; `cargo clippy -p hs-loadgen --all-targets -- -D warnings`
    clean.

  **Rerun it with:**
  ```
  cargo build -p hs-cli --bin hs
  cargo test -p hs-loadgen --test real_client_encrypted -- --nocapture
  ```

## Pre-existing state (built before this session, no status file left behind; summarized here for
the record)

`crates/hs-e2e` already implements, per `crates/hs-e2e/src/routes/mod.rs`'s router:

- Device keys: `POST /keys/upload`, `POST /keys/query` (local users only -- a remote `user_id` is
  silently skipped, not reported in `failures`; federation `/user/keys/query` is a documented seam
  with track 06), `POST /keys/claim` (one-time key first, fallback key second, matching spec
  order), `GET /keys/changes`.
- Cross-signing: `POST /keys/device_signing/upload`, `POST /keys/signatures/upload`. Two
  documented, intentional gaps: signatures are stored and distributed but never cryptographically
  verified (spec says a server "MUST" reject an unverifiable one), and
  `/keys/device_signing/upload` skips UIA re-authentication. Both recorded in that module's own
  doc comment as cut-for-time, not oversights.
- To-device: `PUT /sendToDevice/{eventType}/{txnId}`, idempotent on retry, local delivery only
  (remote-user messages are logged and dropped -- federation delivery is a documented seam with
  track 06), plus a `*` device-id wildcard that broadcasts to every device `hs-auth` knows about
  (not just ones with uploaded e2e keys).
- Key backups (`/room_keys/version`, `/room_keys/keys/...`): full CRUD, `etag`/`count` semantics,
  "replace only if better" session comparison.
- Appservice surfaces: `crate::appservice_feed` (MSC3202 transaction fields: one-time-key counts
  and unused-fallback-key types for an appservice's interested devices) and
  `crate::routes::appservice_proxy` (MSC3983 `/keys/claim` and MSC3984 `/keys/query` proxies,
  sharing the same response-building code as the client-facing routes).
- Storage: `crate::store::tables::TablesE2eStore`, generic over `hs_kv::KvBackend`, with the
  atomic one-time-key claim as the module's centerpiece (serializable-snapshot-isolation based,
  no lock) -- proven under concurrency on both the in-memory and Fjall backends in
  `tests/otk_concurrency.rs`.

**Not implemented yet** (no code found anywhere under `crates/hs-e2e/src`): dehydrated devices
(MSC3814), rendezvous endpoints (MSC4108/MSC4388), the appservice identity-assertion side of
MSC4190 key proxies, and (as this session found) any `hs-user`-side consumption of the device-list
change stream, one-time-key counts, or to-device queue -- all four are only reachable today via
`hs-e2e`'s own client-server routes and MSC3202 appservice feed, never via `GET /sync`.

## Bugs found in other tracks (not fixed here -- out of scope per instructions, reported per
convention)

1. **`hs-user`'s `GET /sync` never includes `to_device`, `device_lists`,
   `device_one_time_keys_count` or `device_unused_fallback_key_types`.** Confirmed live, with
   exact evidence, by `crates/hs-loadgen/src/scenario_encrypted.rs` (see "Done" above and
   `docs/rfcs/0013-e2ee-sync-extensions.md` for the full writeup and the concrete interface asked
   for). Consequence: a real encrypting client can complete every step up through sending an
   encrypted message, but the recipient can never decrypt it (no to-device delivery of the Megolm
   room key), and no client can ever notice another device appearing or a cross-signing key
   changing for a user it shares a room with (no `device_lists.changed`). This is not a new
   discovery in the sense of a surprise -- `crates/hs-user/src/sync/mod.rs`'s own module doc
   already names this exact gap and blames it on `hs-e2e` not existing yet. It now exists; this
   session's contribution is turning that into a live, reproducible failure with an exact root
   cause and a concrete interface proposal, rather than leaving it as a forward-looking comment.
2. Confirmed harmless, not a bug: both loadgen scenarios (`real_client.rs` and this session's
   `real_client_encrypted.rs`) log `matrix_sdk::http_client` `ERROR`-level lines for `404 account
   data not found` during early sync. This is `matrix-sdk` probing for account data
   (secret-storage bootstrap, etc.) that legitimately does not exist yet for a fresh user; the
   404 is correct server behavior and `matrix-sdk` treats it as non-fatal (logged at `ERROR` by
   the SDK itself, not something either scenario can silence). Recorded here only so a future
   reader is not alarmed by it in `--nocapture` output.

## Decisions made

- **`crates/hs-loadgen/src/scenario_encrypted.rs` is a new file beside `scenario.rs`, not a
  modification of it.** Matches this session's instructions and keeps the plain (unencrypted)
  scenario exactly as light as it was (`matrix-sdk` compiled without `e2e-encryption` still works
  for anyone running only `real_client.rs`).
- **The atomicity concurrency probe runs against alice's one-time-key pool, not bob's, and only
  after the real encrypted send.** Bob's pool is the one the real `Room::send` flow claims from;
  exhausting it first via the destructive probe would starve the real flow of a key to claim and
  conflate two different failure modes. Alice's pool is untouched by the real flow (only bob ever
  claims from alice in a scenario where only alice sends a message), so it's the safe target for
  the destructive N+3-concurrent-claims test.
- **The `/keys/claim` atomicity probe and the `/keys/query` shape checks use a small raw
  `reqwest`-based `RawClient` (in `scenario_encrypted.rs`) alongside the two `matrix-sdk`
  `Client`s, authenticated with those clients' own real access tokens.** `matrix-sdk` hides the
  exact wire shape of both responses behind its own types and never fires concurrent overlapping
  claims on its own; both are things this scenario needs to observe directly. This does not
  weaken the "real client" claim: the session, device and token being used are still the real
  ones `matrix-sdk` created via registration and its own automatic key upload -- only the specific
  low-level HTTP calls needed for these two checks bypass the SDK's abstraction over them.
- **`m.room.encryption` is sent via a direct `room.send_state_event(...)` call, not
  `Room::enable_encryption()`.** The latter internally waits on `matrix-sdk`'s own sync-loop
  heartbeat (`sync_beat`), which is fired by a running `Client::sync`/`sync_once` loop; this
  scenario drives `sync_once` explicitly and sequentially (matching `crate::scenario`'s existing
  style), so waiting on a heartbeat that nothing is concurrently producing would be needless
  complexity for the same end result.
- **Cross-signing bootstrap uses `bootstrap_cross_signing(None)` (no UIA auth data).** Matches
  what `crates/hs-e2e/src/routes/cross_signing.rs` actually accepts today (documented as skipping
  UIA re-authentication); once that gap closes (see "Next" #3), this scenario will need updating
  to supply real UIA auth data.
