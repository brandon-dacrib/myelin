Track brief: `docs/workstreams/08-e2ee.md`. Owner crate: `hs-e2e`.

## 2026-10-04 (later): device-list announcements go out as the change commits, a resync is a change and runs in the background, an unknown backup version is not found (branch `agent/e2ee-gaps`)

Graded by Sytest `target/sytest/20261004-wave1/` (main `c2d74174`) and Complement runs 11/16.

**What was wrong, and what changed:**

- **The announcer told servers that joined after a change** ("Local device key changes get to
  remote servers" and "... with correct prev_id", regressions since `1372c71f`; not a regression
  of `5fc19dc5`, but a 200 ms race that commit's timing exposed). `hs-cli`'s
  `DeviceListAnnouncer` polled the stream every 200 ms and worked out the audience when it looked.
  The previous test's user registered (a new device is a change), created a room, and Sytest's
  server joined it within that window; the next look found the user changed *and* sharing a room
  with Sytest's server, and sent that user's device first -- the "Got @USER, expected @USER".
  Now `hs_e2e::store::DeviceKeyStore::subscribe_device_list_stream` (a `tokio::sync::watch`
  of the highest committed position, written by `TablesE2eStore` after each commit that moved
  the stream) wakes the announcer at once; the 200 ms poll stays for another replica's writes.
  The same latency let "If remote user leaves room we no longer receive device updates" pass
  (the remote user's update now crosses before the creator's next sync, usually).
- **A first fetch of a remote list for `/keys/query` was no change** ("Device list doesn't
  change if remote server is down" waits for the remote user in `device_lists.changed` after its
  first query). `federation::resync_remote_user` now records a device-list change whenever the
  fetched list differs from the copy held (devices, keys, names, master or self-signing key; no
  copy differs), as Synapse does after a resync, and nothing when it matches ("our cache matches
  already"; a stale copy is compared like any other).
- **A gap in an inbound update is fetched in the background** (`federation::ResyncQueue`,
  `InboundDeviceList::ResyncScheduled` replaces `Resynced`/`ResyncFailed`). The fetch ran inside
  the `/send` that brought the update. This server's federation client sends one request at a
  time per destination (Synapse's default too), so the `GET /user/devices` to B queued behind
  this server's own transaction to B; with B doing the same, both `/send`s waited on each other
  for 30 s, and B was backed off: wave 1's Complement `TestDeviceListUpdates`, where every remote
  subtest after the first failed on "destination hs2 is backing off". Now the copy is marked
  stale (a query in between asks the user's server), one fetch per user runs on its own task, an
  update arriving meanwhile asks for one more after it, and a failed fetch records a change.
  `E2eState::resyncs_settled` waits for them (tests).
- **A backup version that is not a number** is `404 M_NOT_FOUND` on every read and delete (it
  names no backup; Synapse answers the same), and `403 M_WRONG_ROOM_KEYS_VERSION` on a write
  ("Responds correctly when backup is empty" asked for `bogusversion` and got `400 M_BAD_JSON`).

**Interfaces provided (new or changed):** `DeviceKeyStore::subscribe_device_list_stream` (default
`None`); `E2eState::resyncs_settled`; `federation::ResyncQueue`;
`InboundDeviceList::ResyncScheduled` (replaces `Resynced` and `ResyncFailed`).
`resync_remote_user` now records a change when the list differs. **Interfaces needed:** RFC 0023

announcement (above). **Shared dependencies added:** none.

**Left, and why:**

- **"If a device list update goes missing, the server resyncs on the next one"** is racy by
  construction. Its user has never synced, so its first `sync_until_user_in_device_list` is an
  *initial* sync, which carries no `device_lists` (Synapse's neither), started after the first
  update was handled; the change that sync is waiting for is then behind its token. Synapse
  passes because its resync's three database transactions usually land after Sytest's initial
  sync has taken its token. Here the fetch is now in the background as in Synapse, and still
  lands first (two runs out of two).
- **"If remote user leaves room we no longer receive device updates"** passes when the remote
  user's update crosses within the gap between their key upload and the creator's next sync,
  which returns at once with the leave (2 to 17 ms in the runs here): two runs of three. The
  wave-1 agent's reading (status 05 session 15) is right; the announcer's wake makes it likely
  rather than rare.
- **Durable to-device and device-list EDUs** are track 06's: RFC
  `docs/rfcs/0023-durable-to-device-and-device-list-edus.md` (number to be confirmed at merge).
- **`TestDeviceListsUpdateOverFederationOnRoomJoin` is not done, on purpose.** It wants an
  `m.device_list_update` for the joiner on every join to a room with new servers. Synapse and
  Dendrite skip it (`runtime.SkipIf`, synapse#16875), and doing it would make both Sytest "Local
  device key changes get to remote servers" tests racy again: each awaits "the next
  `m.device_list_update`" after a join and asserts its user and `prev_id`, and Sytest's fake
  server does not buffer EDUs, so a join announcement arriving after the await starts is taken
  for the key upload's.

## 2026-10-02 (later): the arm64-only failure in `federation_edus` was the test, not the copy (branch `agent/device-list-timing`)

`a_device_added_on_one_server_is_a_device_list_change_on_the_other` (`crates/hs-cli/tests/
federation_edus.rs`) failed on CI's arm64 runner since `dd7afc8c` with A's `/keys/query` for bob
answering `{}`. Root cause: bob's login on B creates a device with no keys, which is a
device-list change by itself (the "new device" fix in the entry below), and the key upload a
moment later is a second one. `hs-cli`'s announcer looks at the stream every 200 ms and sends
the difference since it last looked: on a fast machine both changes fall in one tick and go out
as one EDU carrying the keys; on the slow runner the tick landed between them, so A got one EDU
adding the laptop without keys (A had no copy yet, fetched the list, recorded the change) and the
test, told of that change by `/sync`, queried before the second EDU could have arrived. A's copy
was complete and current as of what B had announced, so serving it was right -- Synapse's cache
does the same -- and the test's comment ("A asks B") dated from the design that kept no copy and
so saw B's keys on every query. Reproduced on this desktop by sleeping 300 ms between the login
and the upload: the identical `{}` answer. Not a stale, unapplied or never-fetched copy: those
paths (`resync_remote_user` on a gap, a stale mark, a first query) were checked and are served
by a fetch, never from the copy.

Fix, in the test only: it now waits for A's sync to show the first change before the laptop
uploads its keys (so two EDUs go out every run, which is the path the runner hit), waits for the
second, and asks `/keys/query` until the keys are there with the 15 s deadline every other wait
in that file has (`keys_query_until`; a `failures` entry still fails at once). The other
direction polls the same way. `crates/hs-e2e/tests/remote_device_lists.rs::
a_device_added_without_keys_is_keyed_by_the_next_update_and_nothing_is_fetched_between` pins
the server behaviour in process: after the keyless EDU the query names nothing for the device
and fetches nothing, after the keyed one it serves the keys from the copy. Verified here with
`cargo test -p hs-e2e` (74), `cargo test -p hs-cli --test federation_edus` (4), the test binary
twenty times in a row under six CPU hogs, and the whole file three times while a workspace build ran beside it.

- **No copy of remote device lists** ("Server correctly handles incoming m.device_list_update",
  "...resyncs when client query keys and there is no remote cache", "Device list doesn't change if
  remote server is down", "If a device list update goes missing, the server resyncs on the next
  one"). Sytest's federation server answers `GET /user/devices/{userId}` and expects the server to
  fetch the list there and keep it; this server asked `POST /user/keys/query` on every query and
  kept nothing. Now (`hs_e2e::federation`'s module docs, "Remote device lists: the copy this
  server keeps"; `hs_e2e::store::RemoteDeviceListStore`, tables `hs_e2e.remote_users` and
  `hs_e2e.remote_devices`): while a local user shares a room with a remote user
  (`RoomSharing`, installed by `hs-cli` over the session hub), their list is fetched whole from
  `/user/devices` on first need and kept; an EDU whose `prev_id`s are all at or before the copy's

  list again, a fetch that fails marks the copy stale until one succeeds; a complete copy answers
  `/keys/query` with no request, so the keys still come when the other server is down. A user
  sharing no room is asked of their server every time and not kept, as before; a kept copy is
  dropped at the next query once no room is shared (Complement's `TestDeviceListUpdates`
  property). `m.signing_key_update` replaces the copied master and self-signing keys.
- **Our own `/user/devices` answer** now names every device (keys when uploaded, display name),
  the master and self-signing keys, and `stream_id` is the user's own last change position
  (`DeviceKeyStore::user_stream_pos`, table `hs_e2e.user_stream_pos`), which is also what the
  announcer stamps on the user's EDUs, so a receiver's `prev_id` check lines up.

Branch `agent/federation-to-device`. The "Federation delivery for to-device messages" seam below
is closed, and the cross-signing half of device lists goes out as `m.signing_key_update`.

- **To-device, outbound.** `PUT /sendToDevice` groups messages for users of other servers by
  server and hands each server's share to the installed `hs_e2e::federation::ToDeviceOutbox`
  (`E2eState::install_to_device_outbox`; `hs serve` installs the federation sender) as one
  `m.direct_to_device` EDU with a fresh random `message_id`; a share over 65 000 bytes is split
  per user, then per device, each part with its own `message_id`
  (`federation::direct_to_device_edus`). Without an outbox (federation off) they are dropped and
  logged, and the request still answers `200`.
- **To-device, inbound.** `hs_e2e::federation::receive_direct_to_device(state, origin, content)`:
  the sender must be a user of the transaction's origin; `(sender, message_id)` is marked in the
  existing `hs_e2e.to_device_txn` table under the pseudo-device `m.direct_to_device`, so a

## Session 3 (2026-09-19): cross-signing signature verification

**Task**: `cross_signing.rs`'s module doc said both endpoints stored whatever Ed25519 signatures

signature accepted, and every client trusting this server's copy of another user's keys would
inherit that. Verified against `refs/matrix-spec/content/client-server-api/modules/
end_to_end_encryption.md`'s "Cross-signing" section and
`refs/matrix-spec/data/api/client-server/cross_signing.yaml`'s documented error cases (not from
memory). UIA on `/keys/device_signing/upload` (the module doc's second named gap) was explicitly
out of scope this session -- see "UIA write-up" below.

### What changed

`crates/hs-e2e/src/routes/cross_signing.rs` was rewritten (still the same two handlers,
`post_device_signing_upload` and `post_signatures_upload`) to verify every signature before
storing anything, reusing `hs_model::signing` (`verify_object`, `to_signable_object`,
`verifying_key_from_base64`) and `hs_model::canonical` exactly as `hs-model` already does for
events -- no second canonicalisation was written. `hs-model` and `ed25519-dalek` (already a

### Signature rules enforced

- **A master key is never required to verify against anything.** It is the trust root; the spec's
  `CrossSigningKey` schema itself marks `signatures` "optional for the master signing key". A bare
  `master_key` upload with no `signatures` field at all is accepted.
- **`/keys/device_signing/upload`: a self-signing or user-signing key MUST carry a valid signature
  by the user's master key** -- the one in the same request if given, else the most recently
  *stored* one (per `cross_signing.yaml`'s field descriptions: "must be signed by the accompanying
  master signing key, or by the user's most recently uploaded master signing key if no master
  signing key is included in the request"). No master key available at all (neither in the request
  nor previously stored) is rejected with `M_MISSING_PARAM` ("No master signing key is available",
  the exact wording `cross_signing.yaml`'s 400 response documents). A present-but-unverifiable
  signature is `M_INVALID_SIGNATURE`. Verification happens for *every* key in the request before
  *any* of them is written, so a rejected request leaves all previously stored keys untouched (no
  partial application) -- covered by
  `tests/cross_signing.rs::device_signing_upload_rejects_a_self_signing_key_signed_by_the_wrong_key`.
- **`/keys/signatures/upload`: every signature entry submitted under the caller's own user ID is
  verified before being merged**, with three sub-cases:
  - A signature on a device key is only accepted from that device's own user (`signer ==
    target_user`; there is no key in the whole cross-signing model that lets one user vouch for a
    *different* user's device), resolved against one of the signer's own known keys -- any of
    their three cross-signing keys, or one of their devices (`resolve_signers_own_key`). The
    normal case is the self-signing key; a device is also accepted because the spec explicitly
    allows a user's own device to sign their own *master* key for verification migration, and does
    not name one single fixed "the signer's own material" key for that case either.
  - A signature on **another** user's master key is only accepted if it resolves *specifically* to
    the signer's user-signing key -- not just any of the signer's other real keys. This is the one
    asymmetric rule in the set: it's the single key in the whole model allowed to vouch for a
    different user's identity, so "some real signature by some real key of the signer's" is
    deliberately not good enough here, unlike every other case in this file. Proven both ways in
    `tests/cross_signing.rs`: `signatures_upload_accepts_another_users_master_key_signed_by_the_
    user_signing_key` (accepts a real signature by the real user-signing key) and
    `signatures_upload_rejects_another_users_master_key_signed_by_the_wrong_key_type` (the *same*
    signer, with a *real* user-signing key genuinely provisioned, still gets rejected when the
    signature is by her self-signing key instead -- so the test actually exercises "wrong key
    type", not just "no key at all").
  - A signature on the caller's own master/self-signing/user-signing key (by their own device or
    another of their own cross-signing keys) uses the same general resolver as the device case.
  - A failure in any of these (unverifiable signature, or a key ID this server cannot resolve to
    any key of the signer's at all) is reported as a per-item `M_INVALID_SIGNATURE` entry in the
    response's `failures` map -- a 200 overall, exactly like the pre-existing "no such device or
    cross-signing key" `M_NOT_FOUND` failure, never a request-level error. This matches
    `cross_signing.yaml`'s response schema ("If a signature was invalid, the `errcode` will be set
    to `M_INVALID_SIGNATURE`").

### Signature rules deliberately not enforced this session

- **Structural/schema validation of the key objects themselves** (`usage` array contents, the
  `user_id` field matching the path/caller, "`keys` has exactly one entry" as a named error rather
  than an implicit one). A malformed object simply fails to yield a key ID and public key to verify
  with and is rejected as an invalid/unresolvable signature; it is not given a more specific
  errcode than that. The brief's four bullet points are about *signature* verification, not full
  request-shape validation, and the existing routes already reject the shapes Complement's
  `upload_keys_test.go` checks (missing fields, wrong types) at the JSON-body level.
- **The `403 M_FORBIDDEN` "key ID in use" case** `cross_signing.yaml` documents for
  `/keys/device_signing/upload` (a cross-signing public key colliding with an existing device ID).
  Unrelated to signature verification; not touched.
- **UIA on `/keys/device_signing/upload`.** See "UIA write-up" below -- explicitly out of scope per

## Session 2 (2026-09-19): fixing the three Complement-found bugs

**Task**: `docs/status/14-test-and-conformance.md`'s first full Complement run named three
`hs-e2e` bugs. All three are fixed, each with a router-level regression test proven to fail
against the pre-fix code and pass against the fix; all three are also now confirmed fixed by a
real Complement run (see "Complement subset" below). A fourth, related shape bug
(`/keys/query`'s malformed-filter rejection) and one *new* finding (`/keys/changes` token format,
out of scope for this session, not fixed) were also found while doing this.

### The three fixes

1. **`POST /keys/query` for another user's device keys came back empty.** Root cause:
   `crates/hs-e2e/src/routes/keys_query.rs`'s `build_keys_query_response` only inserted a
   `device_keys.<user>` entry `if !per_user.is_empty()` -- a queried user with zero matching
   devices (never uploaded any, or all filtered out) got no entry in the response at all, not an
   empty object. This is exactly what Complement's `JSONKeyTypeEqual` assertions catch (they
   require the field to *exist*, even as `{}`) -- see `upload_keys_test.go`'s "query for user with
   no keys returns empty key dict". Fixed by always inserting an entry (possibly empty) for every
   requested, valid, local user id. Cross-user queries for a user *with* devices already worked
   (proven by the pre-existing `tests/scenario.rs::two_users_upload_query_and_claim_keys`); the bug
   was specifically the "found nothing" case.
2. **`POST /keys/claim`'s returned one-time-key content didn't match what was uploaded.** Root
   cause: `crates/hs-e2e/src/store/tables.rs`'s `claim_one_time_key` picked the
   *lexicographically first* key id under a device's `(user, device, algorithm)` prefix, not the
   first-*uploaded* one -- a real bug against MSC4225 ("one-time keys must be issued in the same
   order they were uploaded"), reproduced by Complement's `TestKeyClaimOrdering` (uploads key id
   `"1"` before key id `"0"`; a lexicographic claim hands out `"0"` first, the wrong one, with its
   own distinct `key`/`signatures` content -- "the returned key doesn't match what was uploaded"
   is exactly what handing back the wrong key looks like from a client's perspective). Fixed by
   giving every stored one-time key a monotonic upload sequence number (`OtkStored { seq, value }`,
   assigned via a new `"otk_seq"` counter) and having `claim_one_time_key` scan every remaining key
   under the prefix and pick the lowest `seq`, not the first one `range().limit(1)` happens to
   return. The atomic claim-and-delete still happens inside one `hs_kv::transact` closure, so the
   no-double-claim guarantee (`tests/otk_concurrency.rs`) is unaffected -- confirmed by rerunning
   it, still green.
3. **`POST /keys/upload` accepted malformed shapes the spec requires rejected with `400`,** and
   related: **`POST /keys/query`'s per-user device filter accepted an object where the spec
   requires an array.** Two separate fixes, both root-caused to the same class of bug (a shape
   that should be schema-invalid was silently accepted or silently ignored):
   - `keys_upload.rs`: `device_keys` with a missing `algorithms`/`keys`/`signatures` field is now
     rejected with `E2eError::BadRequest` (previously stored verbatim, no validation at all) --
     matches Complement's `upload_keys_test.go` "Rejects invalid device keys". Also added a
     `user_id` mismatch check symmetric with the existing `device_id` one (not directly
     Complement-tested here, but the same class of gap, and cheap to close).
   - `keys_query.rs`: a per-user device filter that is present but not an array (e.g.
     `{"device_id1": true}`, Element iOS's historical bug shape) is now rejected with `400`,
     rather than `Value::as_array()` returning `None` and silently being treated as "no filter" --
     matches Complement's `user_query_keys_test.go::TestKeysQueryWithDeviceIDAsObjectFails`
     exactly (that test's own doc comment names this precise shape).
   - **Also fixed**: `E2eError::BadRequest` mapped to `M_INVALID_PARAM`, not `M_BAD_JSON` --
     the spec's errcode for "the request body doesn't have the shape this endpoint requires".
     Both malformed-shape Complement tests assert the exact errcode, not just the status code, so
     fixing the shape check alone was not sufficient; `crates/hs-e2e/src/error.rs` now maps every
     `BadRequest` to `M_BAD_JSON`. No test in this crate asserted the old `M_INVALID_PARAM` value,
     so this is not a breaking change to anything already relying on it.

### Decisions made (session 2)

- **One-time keys now carry an explicit upload sequence number (`OtkStored`), not just their raw
  value.** The alternative (keeping the raw value and deriving order from, e.g., insertion order
  in a `BTreeMap`) doesn't work: `hs-kv`'s keyspaces have no notion of insertion order, only key
  order, so an explicit counter is the only way to make "first uploaded" queryable at claim time.
  A single global `"otk_seq"` counter (not per-device or per-algorithm) is used since it only needs
  to be monotonic *within* one `(user, device, algorithm)` claim scan, and a global counter trivially
  satisfies that at the cost of one extra `atomic_add` per uploaded key -- not worth a more granular
  counter for this.
- **`claim_one_time_key` now scans every remaining key under a device/algorithm prefix instead of
  taking the first one from a `.limit(1)` range.** This is a real cost increase under a large
  one-time-key backlog (O(n) instead of O(1) per claim), accepted because correctness (MSC4225
  order) matters more than this micro-optimization for a per-device pool that the spec itself caps
  at a small number (clients top up around 50-100 keys, never thousands) -- confirmed the existing
  concurrency proof (`tests/otk_concurrency.rs`, up to 32 concurrent claimants) still passes with
  no timing-related flakiness.
- **`E2eError::BadRequest` now maps to `M_BAD_JSON`, changed from `M_INVALID_PARAM`, crate-wide.**
  Every existing call site (`keys_upload.rs`, `keys_query.rs`, `keys_claim.rs`, `cross_signing.rs`,
  `room_keys.rs`, `to_device.rs`, `keys_changes.rs`) uses `BadRequest` exclusively for "the request
  body doesn't have the shape this endpoint requires," which is precisely `M_BAD_JSON`'s spec
  definition -- not a case-by-case fix, a single correct mapping for the whole error variant.
- **Did not fix `/keys/changes`'s stale token format** (see "New finding" above) -- out of this
  session's explicit scope (the three named bugs, plus a scan of specific other routes that did
  not include `/keys/changes`), and the correct fix depends on `hs-user`'s (track 05's) token
  encoding, which this session did not have time to design an interface for.
- **Did not reconstruct a "before" Complement image for a byte-identical before/after run** (see
  "Complement subset" above) -- the router-level tests already provide a more precise before/after
  proof (isolating exactly the code path in question, not the whole HTTP+container stack), and
  this session's Docker builds were already running 3-4x slower than normal from shared-machine
  contention with other tracks' concurrent builds; a second full build-and-run cycle was judged not
  worth that cost once the router-level proof existed.

`crates/hs-e2e` already implements, per `crates/hs-e2e/src/routes/mod.rs`'s router:

- Device keys: `POST /keys/upload`, `POST /keys/query` (local users only -- a remote `user_id` is

  with track 06), `POST /keys/claim` (one-time key first, fallback key second, matching spec

- Cross-signing: `POST /keys/device_signing/upload`, `POST /keys/signatures/upload`. Two
  documented, intentional gaps: signatures are stored and distributed but never cryptographically
  verified (spec says a server "MUST" reject an unverifiable one), and
  `/keys/device_signing/upload` skips UIA re-authentication. Both recorded in that module's own
  doc comment as cut-for-time, not oversights.
- To-device: `PUT /sendToDevice/{eventType}/{txnId}`, idempotent on retry, local delivery only
  (remote-user messages were logged and dropped then; since 2026-09-28 they go out as
  `m.direct_to_device` EDUs, see the top of this file -- originally a documented seam with
  track 06), plus a `*` device-id wildcard that broadcasts to every device `hs-auth` knows about
  (not just ones with uploaded e2e keys).
- Key backups (`/room_keys/version`, `/room_keys/keys/...`): full CRUD, `etag`/`count` semantics,
  "replace only if better" session comparison.
- Appservice surfaces: `crate::appservice_feed` (MSC3202 transaction fields: one-time-key counts
  and unused-fallback-key types for an appservice's interested devices) and
  `crate::routes::appservice_proxy` (MSC3983 `/keys/claim` and MSC3984 `/keys/query` proxies,
  sharing the same response-building code as the client-facing routes).
- Storage: `crate::store::tables::TablesE2eStore`, generic over `hs_kv::KvBackend`, with the
  atomic one-time-key claim as the module's centerpiece (serializable-snapshot-isolation based,
  no lock) -- proven under concurrency on both the in-memory and Fjall backends in
  `tests/otk_concurrency.rs`.

**Not implemented yet** (no code found anywhere under `crates/hs-e2e/src`): dehydrated devices

`hs-e2e`'s own client-server routes and MSC3202 appservice feed, never via `GET /sync`.

## Decisions made

- **`crates/hs-loadgen/src/scenario_encrypted.rs` is a new file beside `scenario.rs`, not a
  modification of it.** Matches this session's instructions and keeps the plain (unencrypted)
  scenario exactly as light as it was (`matrix-sdk` compiled without `e2e-encryption` still works
  for anyone running only `real_client.rs`).
- **The atomicity concurrency probe runs against alice's one-time-key pool, not bob's, and only
  after the real encrypted send.** Bob's pool is the one the real `Room::send` flow claims from;
  exhausting it first via the destructive probe would starve the real flow of a key to claim and
  conflate two different failure modes. Alice's pool is untouched by the real flow (only bob ever
  claims from alice in a scenario where only alice sends a message), so it's the safe target for
  the destructive N+3-concurrent-claims test.
- **The `/keys/claim` atomicity probe and the `/keys/query` shape checks use a small raw
  `reqwest`-based `RawClient` (in `scenario_encrypted.rs`) alongside the two `matrix-sdk`
  `Client`s, authenticated with those clients' own real access tokens.** `matrix-sdk` hides the
  exact wire shape of both responses behind its own types and never fires concurrent overlapping
  claims on its own; both are things this scenario needs to observe directly. This does not
  weaken the "real client" claim: the session, device and token being used are still the real
  ones `matrix-sdk` created via registration and its own automatic key upload -- only the specific
  low-level HTTP calls needed for these two checks bypass the SDK's abstraction over them.
- **`m.room.encryption` is sent via a direct `room.send_state_event(...)` call, not
  `Room::enable_encryption()`.** The latter internally waits on `matrix-sdk`'s own sync-loop
  heartbeat (`sync_beat`), which is fired by a running `Client::sync`/`sync_once` loop; this
  scenario drives `sync_once` explicitly and sequentially (matching `crate::scenario`'s existing
  style), so waiting on a heartbeat that nothing is concurrently producing would be needless
  complexity for the same end result.
- **Cross-signing bootstrap uses `bootstrap_cross_signing(None)` (no UIA auth data).** Matches
  what `crates/hs-e2e/src/routes/cross_signing.rs` actually accepts today (documented as skipping
  UIA re-authentication); once that gap closes (see "Next" #3), this scenario will need updating
  to supply real UIA auth data.
